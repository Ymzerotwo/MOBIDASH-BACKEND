# المنهج الموحد للواجهة الخلفية (Unified Backend Methodology)

> [!IMPORTANT]
> هذا الملف **القاعدة العامة** التي تُنسخ كما هي إلى أي مشروع. لا يحتوي أسماء مشاريع، ولا أرقام إصدارات،
> ولا مسارات ملفات، ولا أسماء موارد سحابية — كل ذلك مكانه [`PROJECT_PROFILE.md`](../project/PROJECT_PROFILE.md).
> قبل كتابة أي سطر كود: اقرأ البطاقة، ثم الفصل المناسب من هذا الملف.

الرموز المستخدمة هنا محايدة ويُستبدَل كل منها بما يقابله في البطاقة:

| الرمز | المعنى |
| :--- | :--- |
| `<backend>` | جذر مجلد الواجهة الخلفية |
| `<routes>` `<validators>` `<controllers>` `<services>` `<middleware>` `<utils>` | مجلدات الطبقات |
| `<types>` | ملف الأنواع المركزي |
| `<response>` | دالة غلاف الرد الموحد |
| `<db>` `<kv>` `<storage>` `<mailer>` | موارد التشغيل كما هي معلنة في إعدادات المشروع |
| `<check-cmd>` | أمر فحص الأنواع المعتمد في البطاقة |

---

## 0) ترتيب العمل الإلزامي (اقرأ بهذا الترتيب)

1. **بطاقة المشروع** — الحقائق، الأسماء، الأوامر، ونقاط المرجع الفعلية.
2. **الفصل الخاص بمهمتك** من هذا الملف.
3. **الكود الفعلي** عند الشك — لا تفترض شكل دالة أو عمود جدول.

---

## 1) تصنيف المهمة أولاً

قبل أي قراءة أو كتابة، صنِّف الطلب إلى واحد من هذه الأنواع، لأن لكل نوع مساراً ونطاقاً مختلفاً:

| النوع | مخرَجه المتوقع | الفصل المرجعي |
| :--- | :--- | :--- |
| مسار جديد (Endpoint) | Route + Validator + Controller + Service | 2، 3، 5 |
| مخطط تحقق (Schema) | ملف تحقق فقط | 3 |
| استعلام بيانات | دالة خدمة فقط | 4 |
| تعديل منطق تجاري | Service (+ Controller عند الحاجة) | 2، 5 |
| مراجعة أمنية | تقرير + رقع محصورة | 6 |
| توثيق أو تحديث مرجع | ملفات `docs` فقط، مطابقة للكود | 8، 11 |

إن اختلط نوعان (مثلاً «مسار جديد + تعديل جدول»)، فالمهمة **اثنتان** ويُنفَّذان منفصلين.

---

## 2) الطبقات وحدود المسؤولية

الترتيب المعتمد: `Route → Validator → Controller → Service`، مع `Middleware` يلف السلسلة كلها، و`Utils`/`<types>` مشتركة.

| الطبقة | مسؤوليتها | ممنوع فيها |
| :--- | :--- | :--- |
| `<routes>` | تعريف المسار، ربط الوسائط والمخططات، ترتيب التنفيذ | أي منطق تجاري أو استعلام |
| `<validators>` | مخططات التحقق، التقييد، والتطهير عند الحد | الوصول لموارد التشغيل |
| `<controllers>` | قراءة المفحوص، ترتيب الاستدعاءات، تشكيل الرد | SQL أو حسابات مالية |
| `<services>` | المنطق التجاري، الاستعلامات، المعاملات | قراءة الطلب أو كتابة الرد |
| `<middleware>` | فحوصات عابرة للمسارات (جلسة، صلاحية، معدل) | استعلامات جداول تشغيلية أو حسابات فواتير |
| `<utils>` | دوال نقية قابلة للاختبار | حالة عامة أو اتصال خارجي |

**قاعدة الحدود:** الطبقة لا تعرف ما لا تحتاجه — الخدمة لا ترى `c`، والوسيط لا يقرأ جسم الطلب بعد التحقق.

---

## 3) حدود المدخلات: التحقق ثم التطهير

1. **كل مدخل خارجي غير موثوق** — جسم الطلب، الاستعلام، المسار، الترويسات، وبيانات الطرف الثالث.
2. **التحقق عند الحد فقط** — المخطط يعيش في `<validators>` ويُربط في المسار. لا «تحقق مزدوج» لاحق في الكنترولر.
3. **القراءة من المفحوص فقط** — بعد نجاح المخطط، الحقول تُقرأ من مصدر التحقق، لا بإعادة تحليل الجسم.
   - السبب الحقيقي: إعادة التحليل **تتجاوز عمليات التطهير والتحويل** وتعيد بيانات خاماً بلا أنواع.
4. **التطهير مرتبط بالمسار لا بالنية:**
   - قيمة تُخزَّن في قاعدة البيانات → تُطهَّر في المخطط قبل الوصول للخدمة.
   - قيمة تُعرض كـ HTML → تُطهَّر عند الإخراج بما يسمح به السياق.
   - قيمة تُستخدم كنمط بحث → تُهرَّب محارف البحث الخاصة قبل بناء النمط.
5. **كل نص له سقف طول**، وكل معرّف له صيغة متوقعة، وكل كائن مغلق على حقوله المعروفة (لا حقول إضافية تمر).
6. **رسائل الخطأ للمستخدم لا تكشف بنية داخلية** — الكود والتفاصيل الدقيقة تبقى في السجل.

---

## 4) الوصول للبيانات

1. **استعلامات مجهزة بمعاملات فقط** — لا دمج نصوص في SQL، بأي حال، ولا حتى لاسم عمود.
2. **العزل شرط لا خيار** — كل استعلام يخص كياناً مملوكاً لمستأجر/حساب يحمل شرط العزل صراحةً، ويأتي المعرّف من الجلسة لا من العميل.
3. **الكتابات المترابطة ذرّية** — تحديث رصيد + سجل حركة + حالة مستند = دفعة واحدة، لا استدعاءات متفرقة.
4. **الترقيم والحدود** — أي قائمة بلا حد أعلى تعد خطأً، والترقيم جزء من الاستعلام لا من الذاكرة.
5. **الفهرسة بالدليل** — فهرس لكل مسار استعلام مُثبت، ولا فهارس «احتياطية» على أعمدة منخفضة التمييز.
6. **لا قراءة ثم كتابة بلا تحقق** — العمليات المالية تعيد قراءة الحالة داخل نفس الدفعة قبل التعديل.

---

## 5) عقد الردود

غلاف واحد لكل استجابة، ولا استثناءات:

```text
{ success, code, slug, message, data, meta, [details | debug] }
```

- `success` منطقي، `code` رقم الحالة، `slug` مُعرِّف ثابت للحدث، `message` نص للمستخدم، `data` الحمولة، `meta` بيانات الطلب والزمن.
- النجاح والفشل بنفس الشكل — العميل لا يحتاج فرعين للتحليل.
- `details` لمشكلات التحقق فقط، و`debug` لا يظهر في الإنتاج أبداً.
- ممنوع إرجاع كائن خام أو نص مجرد، وممنوع أن يختلف شكل الرد بين مسارين.

## 6) الأمان: الحد الأدنى غير القابل للتفاوض

| المجال | القاعدة |
| :--- | :--- |
| العزل | شرط المستأجر في كل استعلام، والمعرّف من الجلسة |
| الجلسات | كوكي `HttpOnly` + `Secure` في الإنتاج + `SameSite`، وتدوير المُعرِّف عند الدخول، وإبطال شامل عند الطلب |
| CSRF | نمط الكوكي المزدوج + فحص المصدر (Origin/Referer) للطلبات المتغيرة |
| المعدل | محدد لكل مسار حساس، وحظر تصاعدي عند تكرار الفشل |
| المقارنات | مقارنة ثابتة الزمن للأسرار والتوكنات |
| المدخلات | تحقق + تطهير + سقوف طول (حماية من الإغراق والتعابير النمطية) |
| المخرجات | ترويسات أمان، ولا تسريب أسرار أو آثار أخطاء للمستخدم |
| المصادقة | لا رموز وهمية، لا أدوار ثابتة، ولا «تجاوز» لمسار الجلسة |
| الطلبات الخارجية | قائمة نطاقات مسموحة عند جلب روابط خارجية (منع الاستدعاء الداخلي) |
| السجلات | لا كلمات مرور ولا توكنات ولا بيانات شخصية كاملة |

أي استثناء يحتاج قراراً صريحاً مكتوباً في البطاقة، لا اجتهاداً لحظياً.

---

## 7) TypeScript

1. `strict` هو الأساس؛ كل `any` جديد يحتاج سبباً مكتوباً في التعليق أو يُستبدل بنوع حقيقي.
2. **الأنواع مركزية** في `<types>`: الكيانات، مدخلات الاستخدام، وأنواع سياق الطلب — لا ملفات أنواع متفرقة.
3. الحراس (Guard Clauses) أولاً: خروج مبكر عند الفشل بدل تعشيش `if`.
4. `const` افتراضاً، و`let` عند إعادة الإسناد فقط.
5. كل وعد يُنتظر أو يُسلَّم صراحةً — لا `async` طافي بلا `await` ولا `waitUntil`.
6. الكاست (`as`) لتضييق نوع مُتحقَّق منه فقط، وليس لإسكات المترجم.

---

## 8) صفر هلوسة (Zero-Hallucination)

- **لا تخترع** اسم جدول، أو عمود، أو دالة، أو بايندنج، أو مسار ملف. إن لم تجده في البطاقة أو في الكود، فهو غير موجود.
- **لا تُنشئ بيانات** لتشغيل الكود: لا مستخدم ثابت، لا دور ثابت، لا رمز تحقق ثابت، لا رد وهمي. إن احتجت بيانات للاختبار، اطلبها أو ضعها في ملف اختبار معزول.
- **لا تكتب أمثلة كود في الوثائق من رأسك.** كل مثال إما منسوخ حرفياً من ملف موجود مع رابط له، أو لا وجود له.
- إن نقصت معلومة، فالخيارات ثلاثة بالترتيب: اقرأ الملف، ثم اسأل المستخدم، ثم ابحث في المصادر الرسمية — ولا رابع.

---

## 9) بوابة التسليم (قبل أن تقول «انتهيت»)

1. الكود يترجم بلا أخطاء عبر `<check-cmd>`.
2. لا استعلام خارج الخدمة، ولا استعلام بلا حد أعلى، ولا استعلام يخص المستأجر بلا شرطه.
3. المدخلات تمر عبر المخطط، والمخرجات عبر غلاف الرد.
4. لا متغير عام يحمل بيانات طلب، ولا سر مكتوب في الكود.
5. الأنواع الجديدة في `<types>`، والملفات الجديدة في طبقتها.
6. الروابط في الوثائق تشير إلى ملفات موجودة فعلاً.
7. كل سطر جديد في الوثائق مطابق للكود — لا سطر «طموح» بلا تحقق.

---

## 10) بروتوكول الاستيضاح والبحث

- **اسأل ولا تخمّن:** عمود جديد، صلاحية جديدة، سياسة حذف/أرشفة، شكل رد جديد، أو أي متطلب تجاري ناقص → سؤال مباشر للمستخدم.
- **ابحث عند الشك التقني:** سلوك بيئة التشغيل، إصدار مكتبة، ثغرة حديثة → المصادر الرسمية أولاً.
- **لا تخلط الاثنين:** الغموض التجاري سؤال، والغموض التقني بحث.

- أوامر Git بكل أنواعها: بطلب صريح فقط.

- أي أمر يعدّل بيئة التشغيل أو الأسرار: بطلب صريح فقط.
