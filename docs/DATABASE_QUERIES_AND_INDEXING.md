## 1. دورة تنفيذ الاستعلامات وطرق الاستدعاء الأساسية في D1

تعمل D1 وفق نمط صارم: **التحضير (Prepare) $\rightarrow$ الربط الآمن (Bind) $\rightarrow$ التنفيذ (Execute)**.
يُمنع منعاً باتاً دمج المتغيرات كسلاسل نصية داخل SQL. استخدم دائماً علامات الاستفهام `?` كمعاملات موضعية.

### طرق التنفيذ الأربعة ومتى تُستخدم حصراً:
1. **`.first<T>()` أو `.first<T>('column_name')`:**
   - **الاستخدام:** لجلب صف واحد فقط، أو قيمة عمود مفرد مباشرة (مثل `COUNT` أو `balance`).
   - **القاعدة:** يُرجع كائناً أو قيمة مفردة، أو `null` إذا لم يتطابق أي سجل. يجب دائماً إرفاق `LIMIT 1` في الاستعلام لتقليص نطاق الفحص.
2. **`.all<T>()`:**
   - **الاستخدام:** لجلب مصفوفة من السجلات المتعددة (`results: T[]`).
   - **القاعدة:** يُرجع كائناً يحتوي على `results` ومصفوفة الميتا (`meta.rows_read`, `meta.duration`). يجب دائماً تقييده بـ `LIMIT` و `OFFSET` لمنع تحميل آلاف السجلات دفعة واحدة في الذاكرة.
3. **`.run()`:**
   - **الاستخدام:** لعمليات الإدخال (INSERT)، التعديل (UPDATE)، والحذف (DELETE) التي لا تُرجع بيانات.
   - **القاعدة:** يُرجع ميتا التنفيذ؛ يجب دائماً فحص `meta.changes` للتحقق من عدد الصفوف المتأثرة فعلياً (للتحقق من نجاح التعديل أو الحذف).
4. **`db.batch([stmt1, stmt2, ...])` (المعاملات الذرية):**
   - **الاستخدام:** لتنفيذ مجموعة استعلامات متعددة في رحلة شبكية واحدة كـ **معاملة SQL موحدة (All-or-Nothing Transaction)**.
   - **القاعدة:** إذا فشل أي استعلام في المصفوفة، تتراجع D1 تلقائياً عن كافة الاستعلامات (Rollback). يُحتسب الاستدعاء بالكامل كـ **استعلام فرعي واحد (1 Subrequest)** بغض النظر عن عدد العمليات بداخله.

## 2. قواعد استعلامات الإدخال والكتابة (INSERT Patterns)

### أ. كتابة صف واحد في جدول واحد (Single Row / Single Table)
- **القاعدة:** استخدام `crypto.randomUUID()` لتوليد المعرف الأساسي `id`، إلزام تضمين `dashboard_id = currentUser.dashboard_id`، وتحديد التوقيت الزمني `CURRENT_TIMESTAMP` أو ISO string.
- **التنفيذ:** `await db.prepare('INSERT INTO Table (id, dashboard_id, col1, col2) VALUES (?, ?, ?, ?)').bind(id, dashboardId, val1, val2).run();`.

### ب. كتابة عدة صفوف في جدول واحد (Multi-Row / Single Table)
- **القاعدة للكميات الصغيرة (أقل من 20 صنفاً):**
  استخدام استعلام مركب بصيغة `INSERT INTO Table (id, dashboard_id, name) VALUES (?, ?, ?), (?, ?, ?), ...` مع تسطيح مصفوفة المعاملات (Flattened Array).
- **القاعدة للكميات المتوسطة والكبيرة (أكثر من 20 صنفاً):**
  استخدام `db.batch()` بتمرير مصفوفة من الاستعلامات المجهزة المربوطة `db.batch(items.map(item => stmt.bind(...)))`. يمنع ذلك تجاوز حد معاملات SQLite لكل استعلام ويضمن الذرية.

### ج. كتابة صف واحد عبر عدة جداول (Single Row Across Multi-Tables)
- **السيناريو:** العمليات المترابطة (مثل: إنشاء فاتورة + قيد خزينة + خصم رصيد ماكينة).
- **القاعدة الإلزامية:** **حظر تنفيذها باستدعاءات `await` منفصلة ومتسلسلة.**
  يجب دائماً تجميع الاستعلامات في مصفوفة واحدة واستدعاء `await db.batch([insertInvoiceStmt, insertLedgerStmt, updateTerminalStmt])` لضمان عدم حفظ الفاتورة بدون قيد الخزينة عند حدوث انقطاع.

### د. كتابة عدة صفوف عبر عدة جداول (Bulk Transaction)
- **السيناريو:** عمليات البيع الضخمة (رأس الفاتورة + أصناف الفاتورة المتعددة + حركات خصم المخزون + سجلات الأرباح).
- **القاعدة الإلزامية:** تجهيز قالب الاستعلام الأساسي (Prepare) مرة واحدة، ثم بناء مصفوفة كاملة تضم كافة الاستعلامات المربوطة (Bound Statements) وتنفيذها دفعة واحدة عبر `await db.batch([...allStatements])`.

## 3. قواعد استعلامات القراءة والجلب (SELECT Patterns)

### أ. جلب صف واحد آمن (Single Row Lookup)
- **القاعدة:** يجب دائماً اقتران الاستعلام بـ `dashboard_id = ? AND id = ?` مع إضافة `LIMIT 1`، والتنفيذ بـ `.first<T>()`.
- **التحقق:** إذا كانت النتيجة `null`، إرجاع خطأ 404 موحد فوراً (`NOT_FOUND`).

### ب. جلب قيمة مفردة أو عدّادات وإحصائيات (Aggregates & Counts)
- **العد (Counts):** استخدام `SELECT COUNT(*) as c FROM Table WHERE dashboard_id = ?` ثم قراءتها مباشرة بـ `.first<number>('c') || 0`.
- **المبالغ التجميعية (Sums):** يجب دائماً تغليف دوال التجميع بـ `COALESCE` لمنع إرجاع `null` عند خلو الجدول:
  `SELECT COALESCE(SUM(amount), 0) as total FROM Transactions WHERE dashboard_id = ?`.

### ج. الجلب المتعدد والتصفح والفلترة (Paginated Search & Filter)
- **القاعدة:** استخدام الفلترة الديناميكية ببناء مصفوفة شروط `filterClauses` ومصفوفة معاملات `params`.
- **البحث الآمن:** عند استخدام `LIKE`، يجب تطهير النص عبر `escapeLikePattern` واستخدام `ESCAPE '\\'` لمنع ثغرات الرموز الخاصة `%` و `_`.
- **التصفح:** إلزام استخدام `LIMIT ? OFFSET ?` المستخرجين من دالة `getPaginationOptions`.

### د. جلب البيانات المترابطة (JOINs) وحظر كارثة استعلامات N+1
- **حظر الاستعلام داخل الحلقات التكرارية:** يُمنع منعاً باتاً استدعاء قاعدة البيانات داخل حلقة تكرارية (`for / forEach / map`) لجلب بيانات فرعية لكل عنصر!
- **البديل المعتمد:**
  1. إما استخدام `LEFT JOIN` / `INNER JOIN` في استعلام واحد صريح.
  2. أو استخراج كافة المعرفات في مصفوفة وتنفيذ استعلام واحد بصيغة `WHERE parent_id IN (?, ?, ...)`.
  3. أو جلب الجدولين المتوازيين في استدعاء `db.batch([getParentsStmt, getChildrenStmt])` والدمج في الذاكرة بالـ JavaScript.

## 4. قواعد استعلامات التعديل والحذف (UPDATE & DELETE Patterns)

### أ. التعديلات الحسابية والمالية الذرية (Atomic Math Updates)
- **حظر كارثة القراءة والتعديل بالـ JS (Read-Modify-Write Race Condition):**
  يُمنع منعاً باتاً قراءة الرصيد بالـ JavaScript ثم إضافة القيمة وتحديث الجدول بقيمة ثابتة؛ يسبب ذلك تضارباً كارثياً وأرصدة غير صحيحة عند تزامن عمليات الكاشير.
- **البديل الإلزامي:** إجراء الحسابات الحسابية والمالية داخل الـ SQL الذري مباشرة:
  ```sql
  UPDATE shifts 
  SET actual_cash = actual_cash + ?, updated_at = ? 
  WHERE id = ? AND dashboard_id = ?
  ```

### ب. فحص نجاح التعديل والحذف
- بعد استدعاء `.run()`، يجب التحقق من `meta.changes`. إذا كانت القيمة `0`، فهذا يعني أن السجل غير موجود أو لا ينتمي لمتجر المستخدم المصادق، ويجب إرجاع خطأ 404 أو 403.

### ج. تفعيل المفاتيح الأجنبية والحذف المتسلسل (Foreign Keys & Cascades)
- يجب التأكد من تفعيل `PRAGMA foreign_keys = ON;` في بداية كل جلسة وميجريشن.
- عند ربط الجداول، استخدام `ON DELETE CASCADE` للجداول التابعة بحتاً (مثل بنود الفاتورة التابعة لرأس الفاتورة)، واستخدام `ON DELETE SET NULL` أو الحظر للكيانات المستقلة.

## 5. الدليل الصارم للفهرسة في SQLite / D1 (Indexing Strategy)

تعتمد D1 على فهارس B-Tree في SQLite. كل فهرس إضافي يُسرع القراءة لكنه **يُضاعف تكلفة وزمن عمليات الكتابة (Write Amplification)**، لذا يجب الالتزام بالقواعد التالية:

### أ. الأعمدة التي يجب فهرستها حتماً (MUST Index):
1. **معرّف المتجر (`dashboard_id`):**
   - العمود الأهم في كامل النظام لعزل المستأجرين؛ يجب أن يكون جزءاً أساسياً في فهارس كافة الجداول المشتركة.
2. **المفاتيح الأجنبية (Foreign Key Columns):**
   - مثل: `user_id`, `cashier_profile_id`, `invoice_id`, `item_id`.
   - **العلة الهندسية:** في SQLite، عدم وجود فهرس على المفتاح الأجنبي يجبر المحرك على فحص الجدول الابن بالكامل (Full Table Scan) عند كل عملية `DELETE` أو `UPDATE` على الجدول الأب!
3. **الفهارس المركبة للاستعلامات الشائعة (Composite Indexes):**
   - `(dashboard_id, created_at DESC)`: لتسريع ترتيب السجلات والفواتير زمنياً.
   - `(dashboard_id, status)`: للفلترة الفورية للحالات التشغيلية (النشط، المغلق، المعلق).
   - `(dashboard_id, barcode)` أو `(dashboard_id, phone)`: للبحث الفوري الفريد للأصناف والعملاء.
4. **الفهارس الجزئية الذكية (Partial Indexes):**
   - للجداول الضخمة التي يُستعلم فيها جزء صغير متكرر؛ توفر مساحة الذاكرة وتسرع الكتابة:
     ```sql
     CREATE INDEX idx_active_shifts ON shifts (dashboard_id) WHERE status = 'active';
     ```

### ب. الأعمدة التي يُمنع منعاً باتاً فهرستها (MUST NOT Index):
1. **المفتاح الأساسي (`id PRIMARY KEY`):**
   - محرك SQLite ينشئ له فهرس B-Tree فريد تلقائياً؛ عمل فهرس إضافي يدوي عليه هو خطأ وإهدار للمساحة والكتابة.
2. **الأعمدة ذات التنوع المنخفض بمفردها (Low Cardinality Columns Alone):**
   - حظر فهرسة أعمدة الأعلام الثنائية (`is_active`, `is_banned`) كفهرس منفرد مستقل، لأن فحص الفهرس سيكون أبطأ من فحص الجدول؛ تُفهرس فقط كجزء ثانٍ في فهرس مركب مع `dashboard_id`.
3. **حقول النصوص الطويلة والملاحظات (Long Text / Blobs):**
   - يُمنع تماماً فهرسة أعمدة `TEXT` الطويلة مثل `notes`, `receipt_terms`, `description` لأنها تضخم حجم الفهرس وتخنق سرعة الإدخال والتعديل.
4. **الأعمدة سريعة التحديث المتكرر (High Churn Columns):**
   - مثل `last_action_at`؛ كل تحديث يجبر المحرك على تعديل شجرة الفهرس.

### ج. قاعدة الترتيب في الفهارس المركبة (Left-to-Right Rule):
- **الترتيب الصارم:**
  1. أعمدة المساواة (`=`) توضع أولاً في الفهرس (مثل `dashboard_id`, `status`).
  2. أعمدة النطاق والترتيب (`<`, `>`, `BETWEEN`, `ORDER BY`) توضع في نهاية الفهرس (مثل `created_at`).

## 6. قائمة أخطاء الاستعلام الكارثية التي تبطئ نظام D1 (Anti-Patterns to Avoid)

| الخطأ الكارثي | لماذا يبطئ النظام؟ | الحل الإلزامي المعتمد |
| :--- | :--- | :--- |
| **1. استخدام الدوال على الأعمدة المفرسة في WHERE (Non-Sargable)** | كتابة `WHERE LOWER(name) = ?` أو `WHERE strftime('%Y', date) = ?` يُلغي الفهرس ويجبر SQLite على فحص كل صف في الجدول (Full Scan). | مطابقة القيمة النظيفة مباشرة، أو استخدام `COLLATE NOCASE` في تعريف العمود، واستخدام نطاق زمني صريح: `WHERE date >= ? AND date < ?`. |
| **2. البحث بالبادئة العشوائية `LIKE '%abc%'`** | وجود علامة `%` في أول النص يلغي إمكانية استخدام الفهرس تماماً. | عند الضرورة القصوى، يجب دائماً تقييد الاستعلام بـ `dashboard_id = ?` أولاً لتقليص نطاق الفحص إلى سطور متجر المستخدم فقط. |
| **3. استخدام `SELECT *` في الجداول الضخمة** | جلب حقول JSON الطويلة والملاحظات الكبيرة في الذاكرة دون حاجة يستهلك RAM المعالج وباندويث الشبكة. | تحديد الأعمدة المطلوبة بالاسم حصراً: `SELECT id, name, price FROM Items`. |
| **4. استدعاءات متسلسلة بدلاً من `db.batch()`** | تنفيذ 10 استعلامات فردية متتالية بالـ `await` يستغرق 10 رحلات شبكية كاملة ويستهلك حصة الـ Subrequests. | تجميع كافة الاستعلامات وتنفيذها دفعة واحدة عبر `await db.batch([...])`. |
| **5. التعديل غير الذري للأرصدة في كود الـ JS** | قراءة الرصيد ثم حسابه بالـ JavaScript وحفظه يسبب تضارباً وفوارق نقدية بين الكاشيرات. | الحساب الذري المباشر داخل الـ SQL: `SET balance = balance + ?`. |
| **6. إهمال مراقبة `meta.rows_read`** | إذا أرجع الاستعلام صفاً واحداً ولكنه فحص 20,000 صف (`meta.rows_read = 20000`)، فهذا دليل قاطع على نقص فهرس أو كسر الفهرسة. | مراجعة استعلامات الـ WHERE وإضافة فهرس مركب مناسب. |
